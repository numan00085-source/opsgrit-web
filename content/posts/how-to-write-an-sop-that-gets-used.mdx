Most SOPs fail for a simple reason: they are written once, filed away and never trusted again. A usable SOP is short, specific and owned by someone.

## Start from the outcome

Open with one sentence that states what a successful run of this process produces and who depends on it. If you cannot write that sentence, the process is not ready to be documented.

## The SOP template

Use the same structure every time so readers know where to look.

```markdown
# Process name
Owner: <role, not a person>
Last reviewed: <date>
Trigger: <what starts this process>
Outcome: <what "done" looks like>

## Prerequisites
- Access, tools and information needed

## Steps
1. Action verb + object + where to do it
2. ...

## Checks
- How to confirm each critical step worked

## Exceptions
- If X happens, do Y and notify Z
```

## Write steps people can follow at 4 p.m. on a Friday

- Start every step with a verb.
- One action per step.
- Name the exact tool, screen or field.
- Add a screenshot or link only where it removes real ambiguity.

## Assign an owner and a review date

Own SOPs by role so they survive turnover. Put a review date on every document and set a recurring reminder. A stale SOP is worse than none because it teaches people to ignore documentation.

## Test it with a newcomer

Ask someone unfamiliar with the process to follow the SOP without help. Every question they ask is a gap to close. Update the document, then repeat.

## Link SOPs to where work happens

Put the link in the task template, the ticket form or the checklist, not only in a wiki. People follow documentation that appears at the moment they need it.

## Key takeaways

- State the outcome first.
- Keep a consistent template.
- Own by role, review on a schedule.
- Validate with someone who has never done the task.
